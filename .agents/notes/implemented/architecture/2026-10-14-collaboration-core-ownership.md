# Agent 笔记：协作计划与方法修改的 Core 边界

状态：已实现

## 先说结论

协作计划必须由 Lithe 保存和确认，不能由 Agent 上报的任务列表直接替换。
Core 现在提供计划状态转换、限定范围的修改准备和撤销准备，但不启动模型、
写文件或执行测试。这只是协作产品的底层能力，不能宣传成已经拥有强制隔离的自动开发模式。

## 问题

开发者希望亲自编写业务逻辑，让 AI 按确认后的步骤生成映射等配套代码。
两者可能在同一个 Java 文件里。仅限制文件路径不够；仅把禁止修改的方法写进
提示词，也不能阻止外部 Agent 使用命令行直接修改文件。

现有 ACP（编辑器与 Agent 的对话协议）计划条目是 Agent 的运行说明，每次
更新可以整体替换。它没有人的确认版本、分工和验收语义，不能作为写入授权。

## 决策

- Core 提供纯计算命令，输入输出走现有 JSON 契约。原生宿主必须持有可信的
  计划和应用记录，模型只能提出工作项和修改建议。禁止把模型提供的计划当成
  已确认授权，也禁止把模型上报完成当成人工验收。
- 每次确认、暂停、恢复、交接和验收都递增计划版本。旧版本结果不可再次应用。
  人工作业期间没有 AI 写入阶段；主动交接后先进入只读检查。
- 问题挂在对应步骤，确认计划不要求所有未来问题都解决。执行当前步骤前必须
  提交答案，问题和答案一起保留，供后续生成和审查使用。
- 方法范围复用仓库已有固定版本的 Tree-sitter Java 语法解析器，仅用于定位源码
  范围和确认替换没有逃出方法体。类型关系、符号解析、构建和测试事实仍由现有
  Java 工具提供，不新增另一套 Java 语义模型。
- 方法授权包含所属类型和精确声明。修改只能替换完整方法体，不能改变声明、
  导入或类结构。无法解析、签名已变、目标重名、嵌套范围覆盖人工方法时拒绝。
- 撤销使用宿主记录的修改前后内容，不做模糊字符串回退。例如 AI 修改 `map()`
  后，人改了 `core()`，撤销只恢复 `map()`；如果人也改了 `map()`，就报告冲突。
  不要直接恢复整份旧文件，否则会丢掉人后写的代码。
- 命令没有文件系统副作用。多文件准备成功只代表所有输入都通过校验，不代表
  磁盘已经完成原子事务。真正的写入、恢复日志、符号链接检查、未保存缓冲区同步
  和进程隔离必须在原生宿主接入时完成。

## 考虑过的备选方案

- 直接复用 ACP 计划作为分工：结构简单，但模型可以覆盖已确认计划，拒绝。
- 仅按文件分工：实现更简单，但不能满足同一 Service 中分别负责方法的需求。
- 用行号保存方法归属：编辑后位置容易漂移，采用完整类型路径和声明重新定位。
- 自行实现 Java 解析器：现有固定版本语法解析器足够验证源码范围，没有重写理由。
- 用整文件历史恢复撤销：适合用户明确请求恢复文件，不适合自动撤销某个 AI 步骤。

## 后果

底层决策可跨平台复用，普通聊天不会获得新的文件写入能力。方法声明或源码
无法可靠匹配时会暂停，需要重新明确范围，这比猜测位置保守。完整产品仍需要
宿主执行和存储，单独调用这些命令不能证明真实 Agent 无法越界。

本次没有新增下载、缓存目录或运行时存储。输入和结果仅在调用内存中存在，
不会修改安装包、代码签名或 Sparkle 增量更新基线，也没有可注册的跨工作树资源。
