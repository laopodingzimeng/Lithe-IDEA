# Agent 笔记：以人工核心逻辑为中心的协作开发流程

状态：提议中

## 先说结论

目标是在 macOS 的 Lithe 中，为现有 Java / Spring Boot 项目提供真实的人机交替开发。
开发者确认计划与分工、实现核心逻辑，AI 完成配套工作和检查。
当前 Core 与 macOS 原生计划面板已有实现代码；面板支持工作流导入、分步交接和项目进度保存，原生构建与交互验收待完成。本次继续接入了受限 HTTP 模型、原生写入恢复与只读代码分析；真实项目与真实供应商的完整开发验收仍待完成。

## 问题

用户需要把重复劳动交给 AI，同时保留业务设计与核心代码的主导权。
聊天式 Agent 难以持续表达谁负责哪段代码、当前轮到谁、哪些需求尚未澄清，
也不能仅通过提示词保证不覆盖人的修改。

## 提案

1. 用户输入需求，AI 阅读相关项目代码并输出可编辑计划草案；问题挂在工作项下，
   不先进行冗长访谈。AI 建议分工，用户确认后才执行。
2. 独立任务面板显示负责人、状态、涉及文件或方法、验收条件和待确认问题。
   一个项目同时只执行一个计划，其他计划可保存为草案。
3. 分步交替：执行前澄清当前步骤的问题。AI 在确认范围内直接应用配套修改，
   用户查看摘要、差异和检查结果后验收。新增工作项或接口变化必须重新确认。
4. 轮到人时打开相关代码、展示目标和约束，暂停自动任务。只提供需接受的局部
   补全；完整业务实现按用户主动请求提供，不默认填入业务 TODO 或伪代码。
5. 人主动交接后，AI 对照确认需求检查代码正确性与遗漏，说明位置、触发场景和
   修复方向。核心逻辑由人修改。测试场景与预期由人确认，AI 编写并运行测试。
6. 模型执行优先复用已有供应商传输和 Java 工具。协作入口必须使用不能直接
   写源工作区的模型通道，或经验证的进程隔离。仅把 Agent 工作目录切到副本
   不能阻止它通过绝对路径写原目录，因此不能作为强制边界的证明。
7. 宿主校验编辑器版本、文件身份和路径后应用 Core 准备的修改。写入前保存
   恢复意图，逐项记录结果，崩溃后先恢复或展示冲突，再允许执行新步骤。
   状态放平台 Application Support 的工作区专属位置，不写 bundle，不跨 worktree 共享。
   引入实际目录时同步维护资源清单与文档。

正确示例：AI 修改 `OrderService.map()`，用户编写 `createOrder()`；方法声明
需要变化时更新计划，用户确认后继续。不要让一个具有任意 shell 写入能力的
Agent 一边自由改项目，一边声称已由 Core 限制到方法范围。

## 考虑过的备选方案

- 仅聊天清单：难以恢复中断和确认交接，采用独立计划面板。
- 人与 AI 同时自动写代码：容易改变正在依赖的接口，第一版采用串行交接。
- 每次生成先审批补丁再写入：用户已选择计划授权后直接写入、每步完成后审阅。
- 仅凭 Agent 的权限弹窗限制修改：无法覆盖所有命令写入，必须验证执行通道。
- 两端同时交付：第一版先验证 macOS 真实开发，Windows 保留共享契约但不宣称已实现。

## 验收标准

- 真实 Spring Boot 项目完成需求分析、草案确认、配套生成、人工实现、检查、测试和验收。
- 故意尝试越界修改、命令写入和符号链接绕过，源工作区的未授权字节不变。
- 同文件分工、未保存修改、迟到结果、暂停、进程退出、重启恢复和撤销均保留人的改动。
- 需求含糊时只阻塞对应步骤，答案随计划保存；AI 不能自行完成用户验收。
- 按仓库指定 Swift 工具链编译，执行 macOS 测试及产品交互验证；任务结束清理进程。

## 风险

方法级权限只能保护源码修改范围，不能证明辅助方法不会影响核心方法的运行结果，
仍需要需求审查与测试。多文件写入没有天然原子性，必须实现可恢复的宿主事务。
测试和构建本身也可执行项目代码，不能成为绕过源工作区保护的入口。

## 扩展与更新设计

用户明确要求使用桌面原生界面。采用稳定的 SwiftUI 面板与声明式工作流包，
不以浏览器入口或网页套壳交付。工作流包改变步骤、分工、问题、提示词和验收条件，
由桌面原生控件渲染；不能声明任意脚本、窗口组件、命令执行或文件权限。

第一版宿主升级后，用户在“协作 → 导入工作流”载入 JSON 即可更新这些内容。
活动计划固定导入的版本；新版本只能在计划完成或用户明确清除后载入。
新增原生控件、模型执行能力、文件事务或协议语义仍需宿主更新，不能承诺所有功能永远免打包。

### 待办：协作面板重做与原生界面配置

用户已在安装后的桌面中找到协作面板，但反馈界面难看、说明与按钮堆叠，要求先记录，
先验证现有功能，再推进界面调整。此项尚未实现，不应把当前工作流包描述为支持界面更新。

- 按阶段呈现操作：开始只展示需求、模型选择和生成计划；计划阶段展示人工与 AI 的任务卡片；
  执行阶段突出当前任务、代码差异和下一步。版本管理、恢复、清空等放入次级操作。
- 协作面板应直接显示并选择服务商与模型，提供连接检查及配置入口。当前实现复用
  “AI 与提交”的活动服务商，而“AI 服务商”页的下拉框只切换编辑对象；两者容易混淆，
  必须消除隐藏依赖。用户已遇到 HTTP 401，界面应解释认证失败并指向实际使用的配置，
  不能仅显示英文状态码，也不能直接断言密钥错误。操作说明应带用户完成下一步，减少自行探索。
- 下一次宿主升级同时补充原生组件的配置能力，复用 Lithe 现有控件和主题。
  文案、已有组件的布局组合、任务卡片及按钮显示条件应可通过独立配置更新。
  配置仅引用宿主已注册的动作，不扩大模型工具权限，不执行任意代码。
- 界面配置和工作流内容分开管理，并验证版本兼容、无效配置回退和更新后的会话保留。
  配置与状态由平台可写目录管理，不改写安装包；新增原生组件或底层能力仍需打包。
- 验收时实际替换配置并重新加载，确认界面变化、当前计划保留、安装包文件不变；
  同时验证窄面板、深浅主题、键盘操作和各任务阶段，不能只靠截图宣称完成。

例如，调整既有任务卡片的说明和按钮顺序可走配置；增加一种宿主没有的编辑控件仍走升级。
这样既能降低日常调整的打包次数，也能保持桌面原生体验。代价是需要维护配置协议及回退逻辑；
只做一次静态美化无法满足后续扩展要求，使用网页套壳也不符合用户已确认的方向。

后续模型通道、写入事务与检查运行器沿用平台 adapter，Core 负责确定性验证。
当前原生执行使用单独的 HTTP 模型通道与受控补丁接口。复制任务说明与打开普通 Agent 对话仍是人工操作，
普通 Agent 的工具权限不受此计划约束，不能把普通 Agent 的执行结果当作受控执行证据。
完整闭环仍按本文验收标准推进。工作流包支持面与实际验证见原生工作流 Note。
